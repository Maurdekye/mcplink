# Resonite Engine Internals

> Resonite engine execution internals (ILSpy-verified) — component lifecycle ordering (OnAwake/OnInit/OnStart/OnChanges/destroy), immediate vs deferred change events, sync write and drive blocking, the engine update loop and World refresh stages, threading rules, coroutines/awaitables, and physics/collider/grabbing mechanics.

### Source-grounded engine internals (ILSpy-verified, FrooxEngine.dll / Elements.Core.dll)

Deeper mechanics from decompilation — execution order, lifecycle, drive/sync rules, physics gates. Use these to answer "does X run before Y", "why did my write no-op", "why won't it grab".

**Transform pipeline internals (`Slot`).**
- Transform reads are **lazy + bit-cached**: `_transformElementValid` is a bitmask (private enum: `TRS=1`, `Local2Global=2`, `Global2Local=4`, `Local2GlobalScale=0x20`); `EnsureValid*` recomputes only when its bit is clear then ORs it in. Non-uniform-scale escalation invalidates everything except `TRS` (mask `62`).
- The convenience direction setters are **full global-rotation rewrites, not per-axis edits** (`Slot.Forward/Up/Down/Left/Right` set): `Forward` set = `GlobalRotation = floatQ.LookRotation(value, Up)`; `Up/Down/Left/Right` = `LookRotation(value, …) * FromToRotation(...)`. Only one axis is controllable at a time; assigning one clobbers the others.

**Component lifecycle order (`ComponentBase<C>`).** Exact sequence and what each hook may touch:
- `Initialize`: wires base fields then sets `Persistent=true`, `Enabled=true`, `UpdateOrder=InitInfo.DefaultUpdateOrder` → `OnAwake()` → (only if new) `OnInit()` → register for startup. **`OnAwake` fires for both new AND loaded/network-received components; `OnInit` fires ONLY for genuinely new ones.** An exception in either calls `World.FatalError`.
- **RefID allocation is BLOCKED inside `OnAwake`** (wrapped in `ReferenceController.BlockAllocations/UnblockAllocations`) — do `AddSlot`/`AttachComponent`/new sync objects in `OnInit`/`OnAttach`/`OnStart`, not `OnAwake`.
- Startup: `InternalRunStartup` calls `OnStart()` → sets `IsStarted=true` → registers for updates/audio/events → `MarkChangeDirty`. `MarkChangeDirty` is a no-op until `IsStarted`, so **`OnChanges` cannot fire before `OnStart` completes**.
- Destruction order: `OnDestroying` → `OnPrepareDestroy` (after `IsDestroyed=true`, coroutines stopped, members prepared) → `OnDestroy` (under destroyLock; last point you can touch the world) → `Dispose` → `Destroyed` event → handlers nulled.
- `OnAttach`/`OnEnabled`/`OnDisabled` always run inside a `NestCurrentlyUpdating(this)` scope on the engine thread; enabled-change marshals via `RunSynchronously(…, immediatellyIfPossible:true)`.
- **`[UserspaceOnly]` component in a non-userspace world self-destructs and skips ALL hooks** — `CheckUserspaceOnly` short-circuits `OnAttach/OnStart/OnEnabled/OnDisabled/OnDestroy` and queues `Destroy`.

**Change events: immediate vs deferred.**
- A sync write → `MarkChangeDirty` → (on update thread) fires `OnImmediateChanged()` + `Changed` event **synchronously, right then**; the deferred `OnChanges()` runs later in the Changes refresh stage (coalesced once per frame). Use `OnImmediateChanged` for same-call reaction, `OnChanges` for once-per-frame.
- `MarkChangeDirty` called off-thread **auto-marshals** (re-queues itself via `RunSynchronously`, deduped) instead of throwing — the change still eventually fires `OnChanges`, just deferred.

**Sync members, drives & writes (`Worker`/`SyncElement`/`SyncField<T>`/`LinkBase<T>`).**
- Every `Sync<T>`/`SyncRef<T>` field is auto-instantiated (`Activator.CreateInstance` over cached `InitInfo.syncMemberFields`) — non-null after construction without you `new`-ing it; `MarkNonPersistent`/`MarkNonDrivable` applied per cached flag.
- Writing a **driven** field is a **silent no-op** — `SyncField.InternalSetValue` → `BeginModification(throwOnError:false)` returns false; it logs a warning describing the link **only the first time** (gated by `DriveErrorLogged`), so subsequent blocked writes are completely silent. `Sync<T>.ForceSet` does NOT bypass this (it still routes through `BeginModification`; "Force" only forces a change notification). To write a driven field, go through the drive's link or release it.
- **One drive per field invariant**: a drive is `LinkBase<IField<T>>` (`FieldDrive<T> : FieldHook<T> : LinkBase`); `TryLink` returns false if `target.IsLinked` — only `ForceLink` overrides. `IsDriven` is derived from `ActiveLink/DirectLink/InheritedLink`, not a flag. `FieldHook<T>` intercepts writes via a once-settable `SetupValueSetHook` delegate (`IsDriving=false`); `FieldDrive<T>` overrides `IsDriving=>true`. `ReadOnlyRef<T>.ForceWrite` is the only `ForceWrite` in the assembly.
- `BeginModification` guards every sync write: throws if `ModificationBlocked`; at level 0 checks `IsDisposed`, runs `ConnectorManager.ThreadCheck()` (enforces engine thread), then the drive check.
- Built-in base fields on every component: `EnabledField : Sync<bool>`, `persistent : Sync<bool>`, `updateOrder : Sync<int>`. Marker attributes are **unsuffixed type names**: `NonPersistent`, `DontCopy`, `DefaultValue` (`{ object Default }`), `DontDuplicateAttribute`, `RangeAttribute` (`Min/Max/TextFormat` — display only, NOT a clamp). Note: **no `OldNamespaceAttribute` exists in FrooxEngine.dll or Elements.Core.dll** despite the §4 reference to `[OldNamespace]`.

**Engine update loop & threading (definitive ordering).**
- Outer loop `Engine.UpdateStep` has 8 fixed `UpdateStage`s/frame: `UpdateBegin → FrameStart → InputUpdate → GlobalCoroutinesUpdate → WorldUpdate → RenderSubmit → AssetUpdate → Finished`. **Global coroutines run before any world update; render submit is after world updates but before asset updates.** Per-stage time in `Engine.UpdateStageTimes[]`.
- Per-world `World.RefreshStep` is a ~28-stage `RefreshStage` machine, ordered: `RefreshBegin → PhysicsMoved → PhysicsUpdate → PhysicsSchleduleRefine → Coroutines → WorldEvents → UpdatingStreams → PhysicsSync → RunningStartups → RunningEvents → Input → Updates → ProtoFluxRebuild → ProtoFluxEvents → ProtoFluxUpdates → ProtoFluxContinuousChanges → ProtoFluxDiscreteChangesPre/Post → Destructions → Changes → MovedSlots → UserPose → AudioSystem → ParticleSystems → MaterialUpdate → RenderUpdate → ValidatingPermissions → Finished`. So **component `Updates` run before ProtoFlux node updates; Destructions before Changes; change-applications after all Updates.**
- **Queued `RunSynchronously` actions drain BETWEEN every refresh stage** (`NextRefreshStage` → `RunSynchronousActions`), so such an action can run early/multiple-times-per-frame, not once-per-frame; the dequeue count is snapshotted, so actions you enqueue from inside a sync action defer to a later cycle. Exceptions are caught+logged (except `FatalWorldException`).
- **Background/unfocused worlds run a reduced cadence**: `NextRefreshStage` skips `Updates`+`MaterialUpdate` when `!RunFullUpdateCycle` and `Input` when `!ShouldRunFullUpdateCycle`; physics + `ProtoFluxUpdates` are gated the same way (4-cycle `_graceFullUpdateCycles` window). So in a background world, ProtoFlux updates, component Updates, physics, input and material/render can all be skipped.
- Component update order is by **integer `UpdateOrder`, ascending** — `UpdateManager` keeps a `SortedDictionary` of buckets; within a bucket it's list order.
- **A throwing component auto-disables/destroys itself** per `[ExceptionHandling]` (default `ExceptionAction.Disable`): Disable / DeactivateSlot / Destroy / DestroySlot / DestroyUserRoot. `OutOfMemoryException` → `Engine.ForceCrash()`; `FatalWorldException` rethrows. (This is why a buggy component silently turns off mid-session.)
- **Watchdog** (`Engine.Watchdog`, polls every 5s): a ≥10s stall aborts all ProtoFlux contexts in the focused world (`ProtoFlux.AbortAllContexts()`) and dumps state — long ProtoFlux can be force-killed by the engine, not just you.
- **World crash handling** (`WorldManager.UpdateWorld`): a non-userspace world that throws is `EmergencyDump`ed (if authority) + `Destroy`ed + shows a "World Crashed" indicator; **a userspace crash calls `Engine.RequestShutdown()`** (fatal to the engine).

**Coroutines & await helpers (extends §4's ToWorld/Updates).**
- Five awaitable structs, all `IsCompleted=>false` (always suspend ≥1 hop): `ToWorld` (continuation in the Coroutines refresh stage), `ToSync` (sync task queue), `NextUpdate` (defer 1 update), `Updates(n)` (defer n), `ToBackground(WorkType)` (thread pool).
- Awaitables need an **`AsyncLocal` `CoroutineManager.Manager`** established by `StartTask`/`StartBackgroundTask`; awaiting from an arbitrary thread throws "origin CoroutineManager is null". `StartTask` sets `SynchronizationContext` to the manager so plain awaits resume on the **world thread**; `StartBackgroundTask` nulls it (`Task.Run`) so awaits resume on the **thread pool** — but still sets the AsyncLocal so `await default(ToWorld)` gets you back.
- Two coroutine queues: engine-global (`Engine.GlobalCoroutineManager.ExecuteWorldQueue`, runs before world updates) and per-world (`world.Coroutines`, in the Coroutines stage). `Engine.RunPostInit` queues into `FinishInitialization`.
- `Elements.Core.WorkProcessor` (backing `ToBackground`) is a single unbounded unordered `ActionBlock` (`MaxDegreeOfParallelism=-1`, `EnsureOrdered=false`) that **ignores the `WorkType` arg** — so `WorkType.HighPriority` vs `Background` currently has **no scheduling effect**.

**Physics, colliders & grabbing.**
- **`MeshCollider` is static-only**: `PostprocessContactMask` clears the dynamic-collision bit (`mask &= -5`), so triangle mesh colliders can only be Static/Trigger/Character — use `ConvexHullCollider`/primitives for dynamic bodies. Default `Type=NoCollision`, `Sidedness=Front`.
- High-poly mesh colliders lose tunneling protection: `CreateMeshShape` forces `speculativeMargin=0` when `VertexCount > 10000` (or shrinks it from triangle-size metadata). Computed value at `ActualSpeculativeMargin`.
- `PhysicsManager.RaycastOne/RaycastAll` default **`hitTriggers=false`** and **throw `ArgumentException`** on invalid origin/direction/zero-magnitude/NaN-maxDistance (`IsValidRaycast` gate); no-maxDistance overload uses `float.MaxValue`. `IgnoreRaycasts` colliders filtered at sim level.
- Laser/portal traversal: `RaycastExtensions.PortalRaycastAll` recurses through `IRaycastPortal` components (mirrors/portals) up to `maxDepth=10`, accumulating distance; this is how pointers cross mirrors.
- Multiple physics sims exist: `MainPhysicsSimulation` and a dedicated `HapticsPhysicsSimulation`, each with its own raycasts; haptic colliders (`HapticTrigger`/`HapticSampler`/…) run in a separate layer (`Collider.GetSimulation(type)`).
- `Grabber.Grab` grabs only the **single highest `GrabPriority` tier** (sorted CanGrab-first then priority desc; breaks at the first differing priority). `ShouldGrab` rejects a grabbable whose slot `IsChildOf` the grabber or another equal-priority candidate.
- **A driven-but-unhooked transform makes an object ungrabbable** (common footgun): `Grabbable.CanGrab` returns false if `Position_Field`/`Rotation_Field` (and `Scale_Field` if scalable) `IsDriven && !IsHooked`; among many other gates (removed/disabled, IsGrabbed && !AllowSteal, EditModeOnly, user filters, permissions).
- Two-handed scaling: grabbing an object already held by another **local-user** grabber (with `CanScaleHeldObjects`) makes the second grabber a `_scaleReference` (captures `_baseScale`/`_baseDistance`) — scale-by-pulling-apart.
- April-Fools gag (source-confirmed): on `Engine.IsAprilFools` + `MysterySettings.Difficulty == Hard`, `Grabbable.Grab` aborts ~1/3 of grabs (`RandomX.Chance(0.333)`) and nudges `LocalPosition` by `RandomX.OnUnitSphere*0.25` — relevant only if debugging phantom grab failures around April 1.

**Drop reparenting sequence (`Grabbable.Release` + `Grabber.Release`, source-verified).** Where a dropped grabbable ends up, in exact order:
- At **grab** time `Grabbable.Grab` captures `_lastParent = Slot.Parent` and `_lastParentIsUserSpace = (parent == LocalUserSpace)`, then parents under the grabber's `Holder` slot. `World.LocalUserSpace => LocalUser.Root?.Slot.Parent ?? RootSlot` (parent of your UserRoot — usually world root, but a vehicle/platform slot if your root rides one). `Grabber.CreateHolder` attaches a `GrabbableReparentBlock {DontReparent=true, MaxDepth=1}` on the Holder slot.
- **`GrabInstancer.Grab`** never hands you itself: `Instantiate()` duplicates `Template` into **the instancer slot's parent** (→ `LocalUserSpace` if that parent is inside the Template/ContainerTemplate), then calls `Grab` on the copy's `IGrabbable` — so `_lastParent` = the instancer's parent, i.e. an undropped instance tries to land *next to the vendor*. `GrabInstancer.Release` just throws (never called). Template without an `IGrabbable`, or template = another GrabInstancer → exception.
- **On release, per object, in `Grabbable.Release`** (runs FIRST, before any receiver): ① candidate = `_lastParent` if `ReparentOnRelease` (default true; if false candidate stays null). ② if `PreserveUserSpace` (default true) && `_lastParentIsUserSpace` → candidate = current `LocalUserSpace` (overrides ①). ③ candidate child-of-self → `LocalUserSpace`. ④ **reparent-block check**: walk up from candidate (inclusive) via `GetComponentInParentsUntilBlock<IGrabbableReparentBlock>` (stops at a `SearchBlock` or root); if found && `DontReparent` && `candidate.HierachyDepth − block.Slot.HierachyDepth <= MaxDepth` → candidate = `LocalUserSpace`. NB the component lookup does NOT check Enabled — a disabled `GrabbableReparentBlock` still blocks. ⑤ `SetParent(candidate)` — and `SetParent(null)` coerces to `World.RootSlot`, so `ReparentOnRelease=false` ⇒ world root. ⑥ grab events, then `DestroyOnRelease` destroys the slot.
- `IGrabbableReparentBlock` implementers: `GrabbableReparentBlock` (OnAwake defaults `DontReparent=true, MaxDepth=int.MaxValue`), `Grabber` itself (`true`/`1` — why an item snatched from someone's hand drops to your LocalUserSpace instead of back into their Holder), `ItemShelf`, `GrabbableReceiverSurface`, `SnapTarget`, `AssetFrameSlot`, `InteractiveCamera`.
- **Then the receiver pass** (`Grabber.Release` → `InformOfReleasedObjects`, skipped when `supressEvents`): objects with `Receivable=false` are excluded (default true); sphere = holder bounding-box sphere scaled by `ReleaseCheckRadius` (default **1.5**); `SphereOverlap` colliders → `GetComponentInParents<IGrabbableReceiver>` (must be `Enabled && Slot.IsActive`); each object goes to the receiver with **smallest `GetReceiveDistance`** (null = declines), whose `Receive()` re-parents/consumes it — receivers OVERRIDE the step-⑤ placement. Implementers: `ItemShelf`, `GrabbableParenter`, `GrabbableReceiverSurface`, `AssetFrameSlot`, `ProtoFluxGlobalRefProxy`.
- **Finally userspace**: anything unreceived is offered again in the userspace world (point/radius via `WorldManager.TransferPoint/TransferScale`, `RunSynchronously` there) — this is how a drop lands on the dash/inventory UI.
